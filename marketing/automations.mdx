Automations are event-driven workflows that run in the background. A trigger fires (a booking is created, a membership expires, a payment fails), the contact is checked against the automation's entry conditions, and a sequence of steps then runs for that contact: send a message, wait, branch on a condition, add a tag, notify staff. Owners and managers build them, members receive the messages, and staff get notified when a person needs to follow up. Give an automation a **goal** (books again, buys a membership, pays) and it stops messaging a member who reaches it, and the **Performance** tab counts how many did.

## When to use it

Automations take over the follow-ups you would otherwise have to remember by hand. Each one sends at the right moment for each member, without anyone on your team watching the calendar.

Typical uses:

- **Remind members before they train** - turn on the built-in booking reminder so every booking gets an email and app notification 24 hours before it starts.
- **Win back a member who cancels** - a jiu-jitsu gym tags the member **At risk** when they cancel, waits three days, then sends a reason to come back.
- **Collect reviews without nagging regulars** - a padel gym asks players for a review two hours after they check in for a match, paced by sessions played, and invites everyone who leaves one to post it on Google too.
- **Chase a failed payment** - notify your admins and managers, then ask the member to update their payment details.

See [Worked examples](#worked-examples) for step-by-step versions of these, and [Blueprints](#blueprints-prebuilt-automations) for the ready-made workflows behind them.

## How an automation runs

1. A **trigger** event happens in the system (for example, a booking is created).
2. The contact is matched against the automation's **entry conditions** (contact type, tags, pipeline stage, source). If they don't match, nothing happens.
3. A **run** is created and the first step is scheduled. A contact is never in the same automation twice at once.
4. The background worker picks up scheduled steps and executes them in order.
5. Each step records its outcome. A step that errors is tried up to three times before it and its run are marked failed.
6. A run ends early when the contact reaches the automation's **goal** or does one of its **stop when** events. See [Goals and stop events](#goals-and-stop-events).

Each row on the automations list shows how many times the automation has run, how many runs failed, and when it last fired.

## The automations list

Use **Marketing** > **Automations** to view, edit, and create automations. The list is split into two sections:

- **Built-in automations** - Seeded by 1club into every gym (the booking reminder, the membership-expiration reminder, and the marketplace review request). They carry a **Built-in** badge. You can adjust timing, channels, and entry conditions, but the step structure is fixed.
- **Your automations** - Custom workflows you build from scratch, plus any suggested blueprints you have accepted. Available on the Grow plan.

Each row shows the trigger, step count, total runs, failed runs (when there are any), and the last time it fired, plus an **Active** or **Paused** status. Click a row to open it in the builder. To delete a custom automation, open the row's actions menu and choose **Delete**. Deleting cancels any runs still in progress. Built-in automations can't be deleted.

On the Automations page, click into the assistant bar (**What can I help with?**) to see **suggested blueprints**: ready-made workflows (onboarding drip, review request, win-back, and more) that match your gym's setup. Clicking one drops a fully built, paused automation into your list and opens it for review. See [Blueprints: prebuilt automations](#blueprints-prebuilt-automations).

## Triggers

Choose one trigger per automation. The tables below list every trigger with the filters it takes. Every filter is optional: leave it empty and the trigger runs for everything it covers. [Trigger filters](#trigger-filters) explains each filter.

### Bookings and visits

| Trigger | Fires when | Filters |
| --- | --- | --- |
| **Booking created** | A member books a class or area. | Clubs, class types, area types, booked on, first booking only |
| **Booking changed** | A booking is moved or changed and the member is told about it. | Clubs, class types, area types, booked on |
| **Booking cancelled** | A booking is cancelled, by the member or by staff. | Clubs, class types, area types, booked on |
| **Booking checked in** | A member checks in for their booking, or checks in to a class without one. | Clubs, class types, area types, booked on, first visit only |
| **Booking no-show** | A booking is marked as no-show. | Clubs, class types, area types, booked on |
| **Booking completed** | A booked session is over and was neither cancelled nor missed. Fires when the gym's day closes. | Clubs, class types, area types, booked on, first visit only |
| **Visit completed** | A visit is over: a completed booking, or a member's check-ins on a day with no booking behind them (a door scan, a class rung up at the till). Fires once per visit when the gym's day closes. | Clubs, class types, area types, booked on, first visit only |
| **Booking upcoming** | A set time before a booking starts (minutes, hours, or days). Used for reminders. | Clubs, class types, area types, booked on |
| **Check-in failed** | A member's self check-in at a kiosk or check-in tablet doesn't go through. Runs only for a member who was recognized before it failed, since a failure before that has nobody to message. | Clubs |

Use **Visit completed** to follow up on every visit, including members who train without booking. **Booking completed** only reaches members who booked.

### Memberships

| Trigger | Fires when | Filters |
| --- | --- | --- |
| **Membership created** | A new membership starts for a contact. | Plans, clubs, first membership only |
| **Membership cancelled** | A membership is cancelled. | Plans, clubs |
| **Membership expiring** | A set time before a membership ends. | Plans, clubs |
| **Membership renewal upcoming** | One to two days before an auto-renewing membership is charged for its next period. | Plans, clubs, payment method |
| **Membership paused** | A membership is paused. | Plans, clubs |
| **Membership resumed** | A paused membership resumes. | Plans, clubs |
| **Membership expired** | A membership reaches its end and expires. | Plans, clubs |

Use **Membership renewal upcoming** with **Payment method (any of)** set to **None saved** or **Expired** to ask a member to add a card before the renewal fails, rather than chasing a failed payment afterwards.

### Payments

| Trigger | Fires when | Filters |
| --- | --- | --- |
| **Payment succeeded** | A payment is captured. | - |
| **Payment failed** | A payment fails (card declined, insufficient funds, and so on). | - |
| **Payment method saved** | A contact saves a card or another payment method they can be charged to. | - |

### Messaging and reviews

| Trigger | Fires when | Filters |
| --- | --- | --- |
| **Message received** | A contact sends an inbound message. | - |
| **Review submitted** | A member submits a review. | - |

### Progress

| Trigger | Fires when | Filters |
| --- | --- | --- |
| **Promotion or stripe** | A member is promoted to a new level or awarded a stripe on a [progression track](/settings/progression). | Kind: **Promotion** or **Stripe** |
| **Assessment recorded** | A coach saves an [assessment](/members/assessments) with the member notified. Later edits to the same assessment don't fire it again. | - |

### Contact lifecycle

| Trigger | Fires when | Filters |
| --- | --- | --- |
| **Contact created** | A new contact is added. | - |
| **Contact type changed** | A contact's type changes, for example a lead becomes a member. | From type, to type |
| **Pipeline stage changed** | A contact moves to another stage of the [leads pipeline](/members/leads). | From stage, to stage |
| **Account activated** | A contact activates their account: they confirm a sign-up, sign up with Google, Apple, or Facebook, or accept an invitation. | - |
| **Contact birthday** | On the contact's birthday. | - |
| **Tag added** | A tag is added to a contact, by staff or by a [smart tag](/settings/smart-tagging) rule. | Tags |
| **Tag removed** | A tag is removed from a contact. | Tags |

### Smart tags as triggers

Many of the moments worth acting on are [smart tags](/settings/smart-tagging), which 1club applies on its own as members' data changes. Pick **Tag added** and the smart tag under **Tags (any of)** to start an automation when a member reaches one.

| Moment | Smart tag | Smart tag category |
| --- | --- | --- |
| A pass or class pack is almost used up | **Few Sessions Left** | Sessions Left |
| A pass ran out and the member hasn't bought another | **No Sessions Left** | Sessions Left |
| A pause is about to end | **Freeze Ending Soon** | Membership |
| A membership anniversary is coming up | **Member Anniversary** | Membership |
| A membership that won't renew is about to end | **Expiring**, **Expiring Soon** | Membership |
| A member stopped coming | **At Risk** | At Risk |
| A payment is overdue | **Past Due**, **Overdue** | Financial |
| A member is ready for their next level | **Eligible for Promotion** | Progression |

A smart tag can come off and go back on, for example when a member books and then cancels. Set **Days before the same contact can be enrolled again** on the trigger so the sequence doesn't start over from its first message each time.

### Trigger filters

Filters narrow which triggers start the automation by what the trigger is about: which booking, which plan, which gym. [Entry conditions](#entry-conditions) narrow it by who the contact is. Each filter matches any of the values you pick.

| Filter | On triggers about | What it reads |
| --- | --- | --- |
| **Clubs (any of)** | Bookings, visits, memberships, failed check-ins | The gym the visit takes place in: its class's gym, else its area's, else its event's. For a membership, the gym it was sold for. A membership sold for your whole organization counts in every gym. Shown only when you have more than one gym. |
| **Class types (any of)** | Bookings and visits | The class type of the booked class or the class checked in to. A booking for an area has no class type, so it doesn't match. |
| **Area types (any of)** | Bookings and visits | The area type of the booked area, or of the area the class runs in. |
| **Booked on (any of)** | Bookings and visits | Where the booking was made: **Admin**, **Member portal**, **1club App**, **Branded App**, **1club marketplace**, **Website**, **Kiosk**, **Integration**, or **API**. |
| **Plans (any of)** | Memberships | The plan the membership is on. |
| **Payment method (any of)** | Membership renewal upcoming | Whether the member has a payment method the renewal can be charged to: **Saved**, **None saved**, or **Expired**. |
| **Kind (any of)** | Promotion or stripe | **Promotion** or **Stripe**. |
| **From type** / **To type** | Contact type changed | The type the contact moved from and to. |
| **From stage** / **To stage** | Pipeline stage changed | The pipeline stage the contact moved from and to. |
| **Tags (any of)** | Tag added, Tag removed | The tag that was added or removed. |
| **First only** | Booking created, Booking checked in, Booking completed, Visit completed, Membership created | Runs for the contact's first booking, first visit, or first membership only. A booking cancelled before it doesn't count as an earlier one. A first visit is the first time they attended, by booking or by check-in. |

A filter whose answer 1club can't read doesn't match. For example, a class type filter never matches a booking for an area.

## Entry conditions

Entry conditions, shown under **Run only for** in the trigger's settings, filter who the automation runs for after the trigger fires. Every field is optional, and a contact must match all the fields you fill in.

- **Contact has any of these tags** - Only run for contacts who have at least one of the selected tags.
- **Contact is one of** - Only run for contacts of the selected types (members, drop-ins, leads, lapsed members, contacts).
- **In pipeline stage** - Only run for contacts in one of the selected [pipeline](/members/leads) stages.
- **Came from source** - Only run for contacts from one of the selected lead sources.

If none is set, the automation runs for every contact the trigger applies to.

Turn on **Stop when the contact no longer matches** to recheck the conditions before every step. The run ends as soon as the contact stops matching, so a nurture sequence for leads stops when the lead becomes a member instead of messaging them after the next wait.

**Days before the same contact can be enrolled again** keeps a contact out of the automation for a number of days after they last entered it, however that run ended. Leave it empty to let a contact enter again as soon as their last run ends.

## Goals and stop events

A **goal** says what the automation is for, and **stop when** lists what ends it early. Both are set on the trigger, below **Run only for**, and both are made of triggers: you pick a trigger type and, optionally, the same filters that trigger takes.

| | Goal | Stop when |
| --- | --- | --- |
| **What it is** | What you want the member to do, for example book again or buy a membership | Something that makes the rest of the sequence pointless, for example replying to the message |
| **While a run is in progress** | Ends the run as completed, records that it reached the goal, and skips the steps left | Ends the run as stopped early |
| **After the last step** | Still credits the run for a number of days (**Days it still counts after the last step**, up to 30) | Has no effect |
| **Shown on** | **Reached goal** on the Performance tab, and on the run in the History tab | **Stopped early** with the reason "The contact did something that stops it" |

How they behave:

- **Add a goal event** to set a goal. A run reaches the goal when the contact does any of its events. Remove the last event to clear the goal.
- **Add an event** under **Stop when** to add a stop event. A contact who does any of them leaves the automation.
- The trigger that started a run never counts as its goal or as a stop event. An automation that starts on **Booking created** with the goal **Booking created** counts the next booking, not the one that started it.
- An event that is both a goal and a stop event counts as the goal.
- The window after the last step matters for win-backs. The last step is usually the message, and the booking it earns comes later: with a 7-day window, a member who books 3 days after the last message still counts as won back.
- A check-in that staff record after the fact still reaches a goal, since the visit happened. A check-in recorded ahead of the visit doesn't.
- The scheduled triggers (**Booking upcoming**, **Membership expiring**, **Membership renewal upcoming**, **Contact birthday**) can't be goals or stop events, because they're a date coming round, not something the member did.

Examples:

| Automation | Goal | Window | Stop when |
| --- | --- | --- | --- |
| No-show win-back | **Booking created** | 7 days | - |
| Membership win-back | **Membership created** | 14 days | - |
| Failed-payment recovery | **Payment succeeded** | 7 days | - |
| Trial conversion | **Contact type changed** to Member | 14 days | - |
| At-risk member win-back | **Booking created** or **Booking checked in** | 7 days | - |
| Lead nurture by message | **Membership created** | 14 days | **Message received** |

## Steps

Add a step below a node to open the **Steps** palette, pick a step type, then configure it in the right sidebar. Steps run in order, top to bottom, except where a **Condition** step branches the flow.

Messages in **Send message**, **Send form**, and **Notify staff** steps can use variables such as the contact's name and your gym's name. The variables on offer depend on the trigger: booking triggers add the booking's date, time, and resource, and membership triggers add the plan name, renewal price, and expiry date.

### Send message

Send an App, email, SMS, or WhatsApp notification to the contact.

- **Channels** - Pick one or more delivery channels. **App** covers the notification center and an alert on the contact's devices. Email and WhatsApp require the corresponding integration (see [Integrations](/settings/integrations)); SMS requires a sender set up under [SMS](/settings/sms). A text that can't go out (for example no sender for the member's country) doesn't fail the step: its other channels are still sent.
- **Template** - Optionally pick a [message template](/settings/templates) from **System templates** or **Custom templates**. Picking one copies its subject and content into the step, where you can edit them. Later edits to the template do not change what the automation sends. Templates that use variables the current trigger can't fill are greyed out.
- **Subject** and **Content** - The message itself, written inline or starting from the template you picked.

### AI message

Generate the message content with AI at send time, using a rule and tone you provide.

- **AI rule** - What the message should say, for example "Wish the member a happy birthday and thank them for being part of the gym."
- **Tone** - **Professional**, **Friendly**, **Casual**, or **Formal**.
- **Mode** - **Auto-send** generates and sends the message. **Save as draft** generates the message but does not send it, and it does not appear in the [Inbox](/inbox/overview).
- **Channels** - Where an auto-sent message goes.

### Review request

Send a post-booking review request with a single-use link.

- **Channels** - **Email** or **WhatsApp**. SMS is marked coming soon.
- **Instructor message style** - Optionally show a personal chat bubble from the instructor above the review form: **No instructor message**, **Casual & Friendly**, **Professional**, or **Motivational**. Turn on **Send from the instructor's email when possible** to send the email from the instructor's address.
- **Sessions between requests** - Ask again only after the member attends this many sessions, counted across every club in your organization since their last request. Set it to 1 to ask after every session. **Also ask after the member's first session** lets a brand new member hear from you right away instead of waiting out a full interval.
- **Frequency limit** - Cap how many requests a single contact can receive (**Max requests per member**, from 1 to 10) **Per period** (**Week** or **Month**). This is a ceiling on top of the session interval, and a request goes out only when both allow it.
- **Enable Google review conversion** - After a member submits their review, invite them to share it on Google. Everyone who leaves a review is invited, whatever their rating. Only shown for gyms connected to a Google Business Profile.

The two throttles cover opposite cases. The session interval paces the ask by how much a member actually trains, which is what protects infrequent visitors: someone who comes once a month never fills a 7-day window, so a time cap alone would ask them after every single visit. The frequency limit caps the member who trains daily and clears the session interval faster than you want to be asking.

### Send form

Ask the contact to fill in one of your [forms](/marketing/forms), with a single-use link prefilled with what you already know about them.

- **Form** - Only forms with **Sign up** turned off are offered. A sign-up form would ask an existing contact to register a second time.
- **Link valid for (days)** - How long the link works. Defaults to 30 days.
- **Channels**, **Subject**, and **Content** - The message that carries the link. Use the form link and form name variables to place them in the message.

If the form is deleted or later switched to sign people up, the step skips sending and the builder asks you to pick another form.

### Wait

Pause the run for a fixed duration.

- **Duration** - Minutes, hours, or days.
- **Measured from** - **Trigger event**, **Booking start time**, or **Booking end time**. The booking options appear only for booking triggers.

### Wait until

Pause until a condition becomes true, with a timeout.

- **Condition type** - The check that, when true, lets the run continue. The same checks as the **Condition** step. It is rechecked every five minutes.
- **Timeout** - Maximum wait. When it runs out, the step is skipped and the run moves on to the next step.

### Condition

Branch the workflow. The condition is evaluated and the run follows the **Yes** path or the **No** path.

Supported checks:

- **Tag exists** / **Tag does not exist** - Whether the contact has any of the selected tags.
- **Has active membership**
- **Engagement above** / **Engagement below** - Compare the contact's engagement score (0 to 100, built from their recent payments, active memberships and services, visits, and activity trends) to a **Threshold** (50 by default).
- **Booking in period** - Did the contact book in the last N days, hours, or minutes?

### Modify contact

Update the contact in place.

- **Add tag** or **Remove tag**
- **Update field** - Set a contact field to a new value.
- **Move to pipeline stage** - Move the contact to a stage of the [leads pipeline](/members/leads), or remove them from the pipeline.
- **Assign to staff member** - Assign the contact to a staff member, or leave them unassigned.

### Notify staff

Send an App, email, or SMS notification to staff.

- **Who to notify** - **Staff by role** (pick from Administrator, Manager, Front Desk, and Instructor), **Assigned staff member** (whoever the contact is assigned to), or **Class instructor** (the instructor of the booking, available only for booking triggers).
- **Content** - Subject and body, with variables for the contact and trigger event.

## Blueprints: prebuilt automations

A **blueprint** is a prebuilt definition of a complete automation (a trigger plus a full step graph) authored by 1club. A blueprint is never executed on its own - it becomes a real automation only when it is turned into an org-owned row. There are two ways a blueprint reaches your gym: it is either **auto-provisioned** (seeded and locked) or **suggested** (offered to you, and built only when you accept it).

### Auto-provisioned (built-in) automations

Three blueprints are seeded into every gym. They appear under **Built-in automations** and are locked: you cannot rename them, change their trigger or step structure, or delete them. Opening one shows the banner "This is a built-in automation. You can adjust its timing, channels and message."

| Automation | Trigger | Default timing | Channels | State |
| --- | --- | --- | --- | --- |
| **Booking reminder** | Booking upcoming | 24 hours before start | Email, App | Paused |
| **Membership expiration** | Membership expiring | 3 days before expiry | Email, App | Paused |
| **Marketplace review request** | Booking completed | 10 hours after the booking completes | Email | Active |

The two reminders ship **paused**. Sending unconfigured reminders the moment a gym is created would be surprising, so they stay off until you turn them on.

The **Marketplace review request** ships active. It applies only to bookings made through the 1club [marketplace](/marketing/marketplace), asks the member to rate the visit, and never runs for a booking your own review request automation already covers. It has no session interval or frequency limit, since each marketplace booking gets one ask.

For a built-in automation you can change:

- The advance window (how long before the event it fires).
- The channels used by the message step.
- The message subject and content (edit the step directly).
- The entry conditions (tags, contact types, pipeline stages, sources) and **Stop when the contact no longer matches**.
- The on/off state.

The step structure itself is fixed. Editing the message content or timing on a built-in automation, and turning it on or off, is allowed on any plan - that is the point of shipping them. To add steps or branches, build a custom automation alongside.

### Suggested blueprints

Suggested blueprints are never seeded automatically. On the Automations page, click into the assistant bar (**What can I help with?**) and they appear as one-click suggestions above it. They also show in the assistant chat panel when you open it on that page. Clicking one **instantiates** it: 1club builds a fully wired, **paused, editable** custom automation, stamped with the blueprint's identity so the same suggestion won't be offered again. A "Draft created - review and turn it on" message confirms it, and the new automation opens in the builder.

A suggestion appears only when all three are true:

- Your gym is on the **Grow plan** (custom automations require it), and you can manage marketing (the `marketing.manage.club` permission).
- You don't already own an automation from that blueprint (accepting is idempotent - one per gym).
- Every prerequisite the blueprint declares is satisfiable for your gym (see [Prerequisites and gating](#prerequisites-and-gating)).

The catalog of suggested blueprints:

| Blueprint | Trigger | What it does | Goal | Prerequisites |
| --- | --- | --- | --- | --- |
| **New-member onboarding drip** | Contact type changed (to Member) | A three-touch welcome series over the first week (welcome, wait 2 days, tips, wait 3 days, "book your first session"), then tags the member as onboarded. | - | Onboarded tag (created for you) |
| **Review request** | Booking checked in | Waits 2 hours after the check-in, then sends a review request by email (after the first session and every 10 sessions after that, and never more than one a week). | - | Gym runs bookings |
| **No-show win-back** | Booking no-show | Branches on whether the member still has an active membership, then sends a tailored nudge to each path. | Books again, within 7 days | Gym runs bookings |
| **Membership win-back** | Membership cancelled | Tags the member as at-risk, waits 3 days, then sends a win-back message. | Buys a membership, within 14 days | Membership plans exist, At risk tag (created for you) |
| **Birthday celebration** | Contact birthday | Generates a warm, personalized birthday message with AI. The step is set to **Save as draft**, so nothing is sent until you switch it to **Auto-send**. | - | None |
| **Failed-payment recovery** | Payment failed | Notifies your admins and managers, then messages the member to update their payment details. | The payment succeeds, within 7 days | Stripe connected |
| **At-risk member win-back** | Tag added (At Risk) | Reaches out over three weeks to a member who stopped coming, and stops when the At Risk tag comes off. | Books or checks in, within 7 days | At Risk smart tag on, membership plans exist |
| **Trial conversion** | Pipeline stage changed (to your trial stage) | Welcomes the lead, reminds them before their trial, and follows up the morning after depending on whether they came. | Becomes a member, within 14 days | A trial stage in your pipeline, gym runs bookings |

The **Review request** blueprint can also be turned on from the **Marketing** card on [Home](/home/overview): its **Turn on** button creates the automation, activates it straight away, and opens it in the builder. Because it fires on check-in, gyms that don't check members in by hand need **Auto check-in at booking start** in a [booking policy](/settings/booking-policies) for any request to go out.

After you accept a blueprint it lands paused in **Your automations**. Open it in the builder, review and tweak the copy, timing, and channels, then turn it on. Because it is a normal custom automation, you can freely add, remove, or rewire steps.

### Prerequisites and gating

Each blueprint declares typed **prerequisites** - dependencies it needs before it makes sense. Prerequisites fall into two kinds:

- **Providable** - 1club can create the thing for you when you accept. Today this is tags: the tag is found-or-created (scoped to your gym) as part of instantiation, so a providable prerequisite never hides a suggestion. If instantiation fails, any tag it created is rolled back.
- **Gating** - 1club cannot create it, so the blueprint is simply not suggested until you have it.

| Prerequisite | Kind | Satisfied when |
| --- | --- | --- |
| Tag (for example Onboarded, At risk) | Providable | Always - created on accept |
| Gym runs bookings | Gating | You have at least one class or area |
| Membership plans exist | Gating | You have at least one plan |
| Stripe connected | Gating | You have a Stripe integration configured |

So a brand-new gym with no classes, no plans, and no payments connected sees only the blueprints that don't depend on those things (for example the onboarding drip and birthday celebration); the win-back and payment-recovery blueprints appear as you set the rest of the product up.

### Template catalog

The **Send message** step's **Template** picker draws from a template catalog so you don't have to write every message inline. The catalog combines:

- **System templates** - a curated set of 1club-authored message templates that are eligible for automations. If your gym has customized one of these templates, the picker shows your customized version.
- **Custom templates** - your own reusable [message templates](/settings/templates).

Picking a template copies its content into the step, so later edits to the template do not silently change what an existing automation sends. Templates that need variables the automation's trigger can't provide are shown greyed out.

## Building a custom automation

1. Go to **Marketing** > **Automations**.
2. Click **Add Automation**.
3. Give it a name and description.
4. Select the trigger node, pick a **Trigger type**, and configure its options.
5. Narrow the trigger with its [filters](#trigger-filters) if it should run only for some gyms, classes, plans, or a contact's first time.
6. Set **entry conditions** under **Run only for** if you want to limit who the automation runs for.
7. Set a **Goal** and any **Stop when** events (see [Goals and stop events](#goals-and-stop-events)).
8. Add steps from the palette and configure each one in the right sidebar.
9. For each **Send message** step, choose channels and either write content inline or start from a template.
10. Click **Save**.

A new automation starts with the **Active** switch off, so it is saved paused. Review it, then turn it on when you're ready (see [Activating and pausing](#activating-and-pausing)).

## Activating and pausing

New custom automations and accepted blueprints always land **paused** so you can review them before they touch a real member. When you're ready, open the automation, turn on the **Active** switch next to **Save**, and click **Save**. Turn the switch off and save again to pause it without deleting. Pausing is always allowed, so a gym that leaves the Grow plan can still pause the custom automations it built, but it can't turn them back on.

Steps run for real once an automation is active - real emails, real SMS, real staff notifications. If you want to see how a workflow behaves before opening it to your whole audience, narrow the entry conditions to a tag that only a test contact carries, turn it on, trigger the event yourself, then widen the conditions once you're happy.

## Performance and history

Open a saved automation and switch from **Workflow** to the **Performance** or **History** tab to see how it's doing.

**Performance** counts the runs that started in the period you pick:

| Card | What it counts |
| --- | --- |
| **Enrollments** | Each time a contact entered the automation. A contact who entered twice counts twice. |
| **In progress** | Contacts in the automation right now, whenever they entered. |
| **Reached goal** | Runs whose contact reached the goal, while in progress or within the window after, with their share of enrollments. Shown only when the automation has a goal. |
| **Completed** | Runs that finished their steps, or ended by reaching the goal. |
| **Stopped early** | Runs that ended before their last step, broken down by reason. |
| **Failed** | Runs whose step failed after its retries. |

Below the cards, **Enrollments over time** charts entries per day, and **Messages** shows what the automation's messages did on each channel (sent, delivered, clicked, not delivered, unsubscribed).

**History** lists every run with the contact, when they entered, the step they're on, and how the run ended. A run that reached the goal is marked **Reached goal**. Hover a stopped run to see why it stopped:

| Reason | What happened |
| --- | --- |
| The contact no longer matched | **Stop when the contact no longer matches** is on and the contact left the entry conditions. |
| Their step was removed | The step the run was waiting at was deleted from the automation. |
| The automation was turned off | The automation was paused while the run was in progress. |
| The contact did something that stops it | The contact did one of the **Stop when** events. |

## Limits and behavior

- Steps are executed by a background worker that polls every minute. Expect up to a minute of delay between when a step is scheduled and when it runs.
- A step that errors is tried up to three times, with a growing delay between attempts. If the last attempt fails, the step and its run are marked failed and no further steps run.
- Messaging steps are skipped when the trigger was recorded without notifying the customer (for example a booking made by a partner platform). Tagging, staff notifications, and conditions still run.
- For the **Membership expiring** trigger, a **Send message** or **AI message** step is skipped if the membership was renewed, cancelled, or switched to auto-renew between the trigger and the send.
- Completed and cancelled runs are archived after about 90 days; processed trigger events after about 30 days. Failed runs are kept indefinitely so you can investigate.
- A contact is in an automation at most once at a time. Two triggers for the same contact that arrive together, such as two bookings made a second apart, start one run, not two.

## Worked examples

### Membership win-back for a jiu-jitsu gym

A member cancels their unlimited plan. You want a considered follow-up, not an instant plea.

1. Accept the **Membership win-back** blueprint (or build the same shape by hand). It fires on **Membership cancelled**.
2. Step 1 tags the contact **At risk** so you can also see churn on the member list.
3. Step 2 is a **Wait** of 3 days - enough space to feel human.
4. Step 3 sends an email and App notification with a reason to return (a free open-mat week, say).
5. Optionally add a **Condition** on **Tag exists** before the message so members who already resubscribed drop out.

### Post-session review request for a padel gym

You want reviews from players who actually showed up, without nagging regulars.

1. Accept the **Review request** blueprint. It fires on **Booking checked in**.
2. The first step is a **Wait** of 2 hours measured from the **Trigger event** (the check-in), so the ask arrives once they've left the court.
3. The **Review request** step is set to ask every 10 sessions, with **Also ask after the member's first session** left on. A regular who plays four times a week hears from you about once a month; a player who books once a month is asked once after their first match and then not again for the better part of a year.
4. The step also carries a frequency limit of one request per contact every 7 days, which caps the handful of players who train daily and would otherwise clear the 10-session interval every fortnight.
5. Turn on **Enable Google review conversion** so everyone who leaves a review is invited to post it on Google. The invitation goes to every reviewer, whatever their rating, because asking only happy members breaks Google's review policy.

### Birthday message for a yoga studio

1. Accept the **Birthday celebration** blueprint. It fires on **Contact birthday**.
2. The single **AI message** step is set to **Save as draft**, so as shipped it generates each greeting without sending it.
3. When you're happy with the AI rule, switch the step's **Mode** to **Auto-send** so members receive their greeting.

### No-show win-back for a spinning studio

1. Accept the **No-show win-back** blueprint. It fires on **Booking no-show**.
2. A **Condition** on **Has active membership** splits the run: members who missed a class get a light "we missed you, rebook anytime" nudge on the **Yes** path.
3. Contacts with no active membership take the **No** path and get a stronger win-back offer instead.

### Trial conversion for a CrossFit box

You want leads who take a free trial class to join, and you want to know how many do.

1. Accept the **Trial conversion** blueprint, or build it on **Pipeline stage changed** with **To stage** set to your trial stage.
2. The steps welcome the lead, remind them before their trial, and follow up the morning after, with a different message for leads who came and leads who didn't.
3. The goal is **Contact type changed** to **Member** with a 14-day window. A lead who buys a membership midway stops getting trial messages, and one who joins a week after the last follow-up still counts.
4. Check the **Reached goal** card on the **Performance** tab each month to see your trial conversion rate.

### First-visit welcome for a climbing gym

Your members mostly walk in without booking, and you want to welcome each new member after their first session.

1. Create an automation on **Visit completed**, so it reaches walk-ins as well as bookings.
2. Turn on **Only the contact's first visit**.
3. If you run more than one gym, set **Clubs (any of)** so each gym sends its own welcome.
4. Add a **Wait** of 1 day, then a **Send message** step with a tips-and-next-steps message.

### Pack running low for a pilates studio

You want to sell the next class pack before the current one runs out.

1. Turn on the **Sessions Left** smart tag category and set **Few Sessions Left** to 2 sessions.
2. Create an automation on **Tag added** with **Tags (any of)** set to **Few Sessions Left**.
3. Add a **Send message** step offering the next pack.
4. Set the goal to **Membership created** with **Plans (any of)** set to your class packs, so the run ends when the member buys.

## Tips and best practices

- **Start from a blueprint.** Even if you plan to customize heavily, accepting a suggested blueprint gives you a correct trigger, timing, and step graph to edit rather than a blank canvas.
- **Keep automations paused until you've read every step.** Content is copied from templates when you pick them, so proofread inside the builder, not in the template.
- **Give win-backs and conversions a goal.** It stops the sequence when the member does what you asked, and it's the only way to see on the **Performance** tab whether the automation works.
- **Filter the trigger, not the audience, for what happened.** To act on a Gold plan sale, use **Plans (any of)** on **Membership created**. An entry condition only asks what the contact holds, so a Gold member buying a day pass would pass it too.
- **Use entry conditions to avoid overlap.** If two automations react to the same trigger, scope each one with a contact type or tag so a contact doesn't get two messages at once.
- **Anchor waits deliberately.** On booking triggers a **Wait** can measure from the trigger, the booking start, or the booking end. The wrong anchor sends at the wrong moment.
- **Pace review requests by sessions, not just by time.** A time cap alone never fills up for an infrequent visitor, so they get asked after every single visit. Set **Sessions between requests** and keep the frequency limit as the ceiling.
- **Notify staff, don't just message members,** on high-stakes triggers like failed payments - the sooner a human follows up, the more you recover.

## Troubleshooting

| Symptom | Likely cause | Fix |
| --- | --- | --- |
| A suggested blueprint never appears | Its gating prerequisite isn't met (no classes/areas, no plans, or Stripe not connected), or your gym isn't on the Grow plan | Set up the missing piece, or upgrade to Grow. Providable tags are created for you and never block a suggestion. |
| The **Add Automation** button or blueprint accept is blocked | Custom automations require an active Grow subscription | Upgrade the plan under **Settings** > **Organization** > **Subscription**, then retry. |
| You can't accept a blueprint a second time | Blueprints are one-per-gym - you already own an automation from it | Open the existing automation from **Your automations** and edit that instead. |
| An automation is active but nothing sends | The email channel has no integration configured, the SMS channel has no sender for the member's country, or entry conditions exclude everyone | Configure the provider under [Integrations](/settings/integrations) or the sender under [SMS](/settings/sms); loosen or clear the entry conditions. |
| Messages arrive a minute late | The step worker polls every minute | Expected - build in a small buffer rather than relying on second-level timing. |
| A built-in automation won't let you add steps | Built-in (auto-provisioned) automations have a fixed structure | Edit the timing, channels, and content in place; build a separate custom automation for extra steps. |
| A member got two messages from one event | Two automations share the trigger | Add non-overlapping entry conditions (contact type or tag) so only one applies. |
| The review request is on but no requests go out | It fires on check-in, and nobody is checked in | Check members in, or turn on **Auto check-in at booking start** in a [booking policy](/settings/booking-policies). |
| An AI message step never reaches anyone | Its **Mode** is **Save as draft**, which generates the message without sending it | Switch the step to **Auto-send**. |
| A trigger with a class type filter never fires for some bookings | The bookings are for areas, which have no class type | Use **Area types (any of)** for area bookings, or add a second automation. |
| **Only the contact's first booking** skips a new member | They booked before, for example as a lead | Expected - the filter means the first booking ever, at any gym. Use **Contact type changed** to Member for a new-member welcome. |
| **Reached goal** stays at zero | The goal events don't match what members do, or they act after the window | Check the goal's filters, and lengthen **Days it still counts after the last step** (up to 30). |
| The trigger that started a run didn't count as its goal | By design: the starting trigger never counts | Expected - the goal counts what the contact does next. |
| **Check-in failed** never starts a run | Most failures happen before the member is recognized, so there's nobody to message | Expected - only failures after the member scanned their card or code start a run. |
| A member gets the same sequence again and again | Its smart tag comes off and goes back on | Set **Days before the same contact can be enrolled again** on the trigger. |
