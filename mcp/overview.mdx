The Model Context Protocol (MCP) is an open standard that lets an AI assistant call real software instead of guessing. 1Club runs MCP servers so an assistant like Claude or ChatGPT can look up your classes, check availability, read your transactions, and create bookings, using your own data and your own permissions.

You connect once, and from then on you can ask an assistant things like "which classes next week still have space?" or "book court 2 on Thursday at 18:00 for Maria" and it uses 1Club to answer, rather than making something up.

## Two servers, two audiences

1Club exposes **two separate MCP servers**. Each has its own address, and an assistant connected to one never sees the other's tools.

| Server        | Address                          | Who it is for                                    | Authentication             |
| ------------- | -------------------------------- | ------------------------------------------------ | -------------------------- |
| **Admin**     | `https://mcp.1club.ai/admin`     | Your gym's staff and internal systems            | 1Club API token (required) |
| **Discovery** | `https://mcp.1club.ai/discovery` | Anyone searching the public 1club.me marketplace | None                       |

- The **admin server** reads and writes one organization's own data. Every tool requires an API token, and every response is limited to the organization that token belongs to. This is the one you want for running your gym.
- The **discovery server** searches the public marketplace across all listed gyms and checks published availability. It is anonymous by design and can never reach a single organization's private data.

Pick the one that matches what you are trying to do, then follow [Connect an assistant](/mcp/connect).

<Note>
  The root address `https://mcp.1club.ai` is not itself a connectable server. If
  you point a client at it, the connection fails with a message naming the two
  addresses above. Always include `/admin` or `/discovery`.
</Note>

## What an assistant can do

The admin server currently covers reads across your schedule, content, gyms, and revenue, plus booking actions:

- **Classes** - list your classes and open a single one.
- **Areas and availability** - list bookable areas and check when they are free.
- **Bookings** - create a booking, cancel a booking, and look one up.
- **Gyms** - read a gym's details, amenities, and rating.
- **Content** - read published website and CMS content.
- **Transactions** - list and open billing transactions.

The full list, with the token scope each one needs, is on the [Tools reference](/mcp/tools) page.

The discovery server covers marketplace search and public availability for classes, areas, and instructors.

## What it cannot do yet

- **There is no member-facing server.** An API token represents your organization, not a person, so an assistant cannot currently act "as" a specific member in the portal or the marketplace. That needs per-user sign-in and is planned separately.
- **Coverage is deliberately narrow.** The admin server is built strictly on the documented [Platform API](/api-reference/introduction), so an assistant can only reach what that API exposes. Anything outside it, such as members, memberships, messaging, or automations, is not reachable through MCP yet.
- **Writes are limited to bookings.** Everything else is read-only.

## Security model

- **A token is a key to your organization.** Anyone holding it can do what its scopes allow. Treat it like a password and store it in your assistant's credential field, never in a shared document or a chat message.
- **Scopes are the limit.** An assistant can only use tools whose scope is on the token. A token with `classes:read` cannot create a booking, no matter what the assistant is asked to do. Grant the narrowest set that does the job, and prefer read-only tokens unless the assistant genuinely needs to book.
- **Revocation is instant.** Revoking the token in **Settings > APIs and MCP** cuts the assistant off immediately.
- **Assistants can be talked into things.** Content the assistant reads, such as a member note or a website page, can contain text that tries to steer it. This is why a read-only token is the safe default, and why write scopes belong only on connections you supervise.
- **Rate limits apply.** MCP calls count against the Platform API's limit of 100 requests per minute per organization.

## Before you start

- API access is a **paid feature**. On the Free plan or during a trial you can view and revoke existing tokens, but you cannot create one, so the admin server cannot be connected. The discovery server needs no token and works for anyone.
- Creating a token requires the **settings.manage.organization** permission. In practice that means admins and owners.
- Your MCP client must support **remote (HTTP) MCP servers** with a bearer token, or be able to run a local server. [Connect an assistant](/mcp/connect) covers the clients that do.
